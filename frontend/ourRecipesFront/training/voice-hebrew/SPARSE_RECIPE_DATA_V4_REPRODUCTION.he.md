# שחזור השוואת נתוניםv4

הפרוטוקול הקובע: [תוכניתv4](SPARSE_RECIPE_DATA_V4_PLAN.he.md). מקור, נתונים, תוכניות זרוע וגיבובים הוקפאו ב־`2af4c8b` לפני הקצאתGPU. אין לשכתב את קובצי המקור או את הנתונים אחרי צפייה בתוצאה; שחזור במיקום/גרסה אחרים מקבל תוכנית נגזרת ושם ריצה חדש.

## בדיקות ללא מודל

מהתיקייה `frontend/ourRecipesFront/training/voice-hebrew`:

```sh
python -m unittest discover -s tests -p 'test_sparse_recipe*.py' -v
```

17 בדיקות חוזה/נתונים/מדדים, לא בדיקת איכות של מודל. `sparse_recipe_data_v4.build()` מחזיר נתונים דטרמיניסטיים; יש להשוותJSON מרונדר לבתים הקפואים, בלי להפעיל גנרטור שדורס קובץ קיים. המקור מסרב לדרוס. טיוטת הכנה קודמת לא שימשה להסקה/אימון, ונשמרה בנפרד בריצה מוחרגת.

בדיקתprefix ותקציב עםtokenizer ציבורי מקומי מה־revision המוגדר, בלי משקולות:

```sh
python -B sparse_recipe_preflight_v4.py \
  --tokenizer /absolute/local/Qwen3-tokenizer \
  --output /new/path/preflight.json
```

אין צורך להתקין סביבה חדשה לצורך בדיקות הקוד בלבד. בודקtokenizer דורשTransformers. הרצה מקורית השתמשה בסביבת3.12 הקיימת לבודקtokenizer, וב־3.13 לאימון. מקורמודל, משקולות1.50GB וגיבובים מפורטים בתוכניתv3 ובתוכניות הזרוע; המשקולות מורדות רק לשרתT4. רישיוןApache2.0 ומקור ציבורי קפוא נשמרו ב־verification/qwen-sparse-source-20261116.

## הרצתT4

נדרשת הרשאתColab קיימת, יתרה זמינה ו־SSH CLI שהוגדר מראש. שמות ונתיבי credentials בדוגמה הם מצייני מקום; הם אינם בחבילת המסירה.

```sh
GOOGLE_APPLICATION_CREDENTIALS=/absolute/private/authorized-user.json \
python -u sparse_recipe_colab_v4.py \
  --session ourrecipes-sparse-v4-replay-unique \
  --ssh-identity /absolute/private/ssh-key
```

ה־owner יוצרT4 ששמה ניתן, מתקין venv נפרד, מאמת את המקורות והנכסים, מריץcontrol ואזdiverse ומשחרר את הסביבה בסיום/כשל. אין לשנות מנוי, לרכוש יחידות או להחליףGPU כדי לשחזר. איןDrive mount, פרסוםHub או העלאתcredentials/אודיו. לוגי חשבון ו־sessions נשמרים רק בריצה המוחרגת ולא נכללים בארכיון המחקר.

המנוע המקורי `sparse_recipe_sft.py` נשאר ללא שינוי. wrapperv4 מחליף את ההנחיה באופן זהה בשתי הזרועות, מפנה לתוכנית/נתונים המתאימים ומוסיף מדידתdiagnostic/regression. האופטימייזר, כימות בזמן אימון, LoRA, seed, masking, תקציב פלט ושניcheckpoint נשארים זהים. זו אינה טעינתהמשך שלcheckpointv3. לשתי הזרועות אותו גוף ציבורי מקורי ומתאם מאופס חדש.

## תוצרים ואימות

`runs/SESSION/results.zip` הוא ארכיון המקור עם תגובות, עקומות וארבעהcheckpoint כוללoptimizer/RNG. `archive-manifest.json` מאמת את הארכיון; בתוך הארכיוןMANIFEST נוסף מאמת כל חבר. הבסיס הציבורי וקובצי התלויות אינם משוכפלים אליו. `recovery.json` רושם אם המשקולות חולצו גם לתיקייה או נשמרו רק בארכיון עקב מקום.

```sh
python sparse_recipe_audit_v4.py runs/SESSION \
  --output verification/sparse-recipe-results-v4-replay.json
```

כלי הדוח מסרב לדרוס קובץ, בודק את כל הגיבובים, מזהי המקרים וחלוקת40/120/120, מחשב מדדים מחדש, בודק סדר640 אינדקסי הדוגמאות בכל זרוע וזהות הבסיס. התוצאה העיקרית היא160 בשתי הזרועות, גם אם המנוע צייןbest80. תגובות0 נבדקות לזהות כדי לזהות שונות עוד לפני שינוי משקולות.

הדוח משמר גם מונה שינוי מוצע שגוי שנבדק מול המצב הקודם והצפוי. `unsafe_state` המקורי אינו מונה כזה, כפי שתועד ב־v3. שמירתcheckpoint/RNG אינה טענה ששחזור אימון מאמצע נבדק; הוא טרם נבדק כאן.

חבילת המסירה יכולה להכיל את `results.zip` כארכיון מקונן. מספיק למקם אותו ואתarchive-manifest תחת אותונתיבריצה ולהריץaudit; אין צורך לחלץ משקולות לצורך בדיקת מדדים. בדיקות המסירה מחלצות רק מקורות וקובציJSON קטנים, ומאמתות את בתיהארכיון הגדול בלי לשכפל אותו פעם נוספת.

מבחני המוצר השמורים, עברית טבעית, קול, כימות, דפדפן וטלפון אינם חלק משחזור זה. אין להסיק זמני טלפון מ־GPU או מציון על דוגמאות תלויות.
